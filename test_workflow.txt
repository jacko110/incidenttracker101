NIB BROWSER WORKFLOW CHECKLIST
================================

Purpose
-------
Use this checklist to manually verify sign-in, incident creation, attachments,
case search, and role-based case actions in a browser. Mark each step PASS or
FAIL and note any error message or unexpected behavior.

Before you start
----------------
1. Open a terminal in the project root.
2. Start the backend:
     cd backend
     npm install
     npm run seed
     npm start
   The seed command creates the local demo accounts and sample cases. Use it
   only with a development database. The backend should report that it is
   listening on http://localhost:4000.
3. Open a second terminal in the project root and start the frontend:
     cd frontend
     npm install
     npm run dev
4. Open http://localhost:5173 in your browser.
5. If the browser shows an API or network error, confirm both terminals are
   still running. Do not run the seed command against data you want to keep.

Basic sign-in and session checks
--------------------------------
[ ] 1. Sign in as zemenu. Confirm the dashboard loads and shows the signed-in
       username and SOC Analyst role.
[ ] 2. Refresh the page. Confirm you remain signed in and the dashboard loads.
[ ] 3. Sign out, then sign in as iranalyst. Confirm the account and role shown
       in the sidebar are correct.
[ ] 4. Sign out, then sign in as admin. Confirm the account and role are correct
       and User Management appears in the sidebar.
[ ] 5. As zemenu, try opening /users directly in the address bar. Confirm the
       app returns you to the dashboard and does not show user management.

Create an incident with an attachment
--------------------------------------
[ ] 6. Sign in as zemenu and open Incident Panel, then choose Create case.
[ ] 7. Complete the required incident details. Add source and destination IPs,
       date and time, asset, origin, attack type, severity, shift, HTTP status,
       summary, impact, and recommendations.
[ ] 8. Continue to Add IOCs. Add an IOC type and threat intelligence source.
[ ] 9. Upload a small image or document (under 10 MB) to the IOC. Confirm the
       filename appears, then add the IOC.
[ ] 10. Continue to Review and inspect the incident and IOC details. Submit.
[ ] 11. Confirm the new case detail page opens and displays the incident data.
[ ] 12. Open the attachment from the case. Confirm it loads while signed in.
       Remove the ?token=... query string from its URL, then open that URL in
       a private/incognito window; confirm access is denied. A copied URL that
       still contains a valid token grants access, even in incognito. Treat
       token-bearing URLs as credentials and do not share them.
[ ] 13. Try submitting a second incident with a required field missing. Confirm
       the form explains what needs to be completed and does not create a case.

Search and navigation
---------------------
[ ] 14. Use the top-bar Search cases field to search for a distinctive word
       from the new case title. Press Enter. Confirm the case list shows the
       matching result and the browser URL includes ?q= with the search term.
[ ] 15. Refresh the search results. Confirm the search term and results remain.
[ ] 16. Clear the case-list search. Confirm the result list updates.
[ ] 17. Use each Case list sidebar filter and confirm only its matching status
       is highlighted. Open My cases and confirm only My cases is highlighted.
[ ] 18. On a narrow/mobile browser window, open the navigation, follow a link,
       and confirm the menu closes. Confirm the page remains usable without
       horizontal overflow.

Role-based actions
------------------
Assignment (SOC Admin only)
[ ] 19. As admin, open the case created above. Assign it to an active user.
       Confirm the assignee changes and an assignment activity entry appears.
[ ] 20. As zemenu or iranalyst, open the same case. Confirm assignment controls
       are not available. If you try the assignment API action through the UI,
       it should be denied.

Rejection (SOC Admin and IR Analyst)
[ ] 21. As zemenu, confirm Reject is not available in the Incident Panel or case
       detail page.
[ ] 22. As iranalyst, reject a test case and enter a reason. Confirm it appears
       under Rejected by IR Analyst and its activity history records the action.
[ ] 23. As admin, reject a different test case. Confirm it appears under
       Rejected by SOC Admin.
[ ] 24. Confirm a rejected case cannot be rejected again from the new-incidents
       view. Confirm ordinary status controls do not let an analyst mark a case
       Rejected without using the permitted reject action.

Archive and restore (SOC Admin only)
[ ] 25. As admin, archive a test case. Confirm it leaves the active case list
       and appears in Archive.
[ ] 26. Restore the archived case. Confirm it returns to the active case list.
[ ] 27. As zemenu and iranalyst, confirm archive/restore controls are hidden and
       unavailable.

Session and error handling
--------------------------
[ ] 28. Sign in, then have an admin deactivate that account from User
       Management. On the deactivated account, make another API-backed action
       or reload the page. Confirm the session ends and login is shown.
[ ] 29. Sign in again, then have an admin change that user's role. Make an
       admin-only request using the existing session. Confirm the new role is
       enforced immediately; a permission-denied response should not sign the
       user out.
[ ] 30. Stop the backend while viewing a page, then trigger a data refresh.
       Note whether the page gives a clear error and recovers after the backend
       is restarted.

Automated verification (2026-09-28)
-----------------------------------
Run from the project root:
  npm --prefix backend test
  npm --prefix frontend test
  npm --prefix frontend run build

The backend workflow suite uses real HTTP requests, an in-memory SQLite
database, temporary uploaded files and offline email logging. It never seeds
or edits the development database and does not send real email.

Covered: login and role enforcement; incident/IOC creation, search, edits,
notes and history; assignment and account deactivation; notification ownership;
rejection, archive and restore; pagination and dashboard date filters; deadline
permissions and workload; reminder deduplication, overdue catch-up and email
opt-out; bidirectional case links; multipart attachment contents, access and
limits; chat; admin user creation/password reset; critical-incident alerts;
and transaction rollback when audit insertion fails.

Frontend checks cover session invalidation, preserving sessions on permission
or network failures, retry recovery, and paginated/filter-preserving API calls.

The API checks alone do NOT mark the browser checklist above PASS. Reminder
tests invoke the real service directly rather than waiting an hour.

Browser regression suite (Chromium)
-----------------------------------
From the project root:
  npm install
  npx playwright install chromium
  npm run test:e2e

Or run all automated verification:
  npm run verify

Browser coverage: Nib branding/title, login/refresh/logout, protected admin
routes, required incident fields, full incident wizard with uploaded evidence,
attachment contents, notes, status changes, analyst action visibility, search
persistence after reload, admin assignment/deadline persistence, due-soon list,
mobile navigation closing, and case-list/incident-form viewport width at 390px.

The suite uses separate temporary data and test ports 4015/5175. It does not
modify development records or send email. Screenshots/traces are retained on
failure in test-results/. Other browsers, the remaining manual scenarios,
external-provider SMTP delivery and hourly wall-clock timing are not covered
by these browser tests. Process restarts are covered separately below.

policy-audit rollback and the browser configuration/application workflow.


Overdue escalation
------------------

       hourly check or restart the development backend. Confirm each active SOC
       Admin receives one escalation notification linked to the case.
[ ] 53. Open the case. Confirm the escalation timestamp and Activity History
       entry list the admin recipients. Repeat the check/restart and confirm

[ ] 54. Confirm inactive admins receive no escalation. Disable an active admin's
       email preference and confirm their in-app escalation still appears.
[ ] 55. Confirm unassigned overdue cases escalate, but completed, rejected,
       archived and future-deadline cases do not.
[ ] 56. Change the deadline to another past timestamp. Confirm the escalation
       marker clears and the next check sends one new escalation. Saving the

Automated coverage: backend/test/escalation.test.js, the manual deadline checks
in sla.test.js, and the local SMTP/process-restart scenarios in
delivery-restart.test.js. SMTP failures preserve the in-app alert and history;
email retrying is not part of this feature. Scheduling runs hourly, accelerated
only in isolated tests. No external email or development records are used by
the automated checks.
